## What this is

Cosmic Engine — a real-time, audio-reactive visual engine for live music performances (see `../Vision`). It listens to two guitar inputs via an audio interface, does FFT analysis, and drives GLSL fragment shaders ("worlds") that are projected/displayed live. There is no offline/batch mode — the intended runtime experience is a fullscreen visual synced to a live audio signal.

## Commands

Run from this directory (`CosmicEngineApp/`, which contains the `.csproj` — still named `CosmicEngine.App.csproj`, unchanged; the `.sln` lives one level up). Note: this folder was renamed from `CosmicEngine.App` to `CosmicEngineApp` (Desktop Launcher Usability Pass, Entry 23) — a folder ending in `.App`/`.app` (case-insensitive) makes macOS Finder mistake it for a broken application bundle and refuse normal navigation into it. The `.csproj` filename, C# namespace (`CosmicEngine.App.*`), and `.sln` project display name were deliberately left unchanged - only the directory name changed.

```bash
dotnet build          # build
dotnet run             # run — opens a window, starts audio capture, and starts the control server
dotnet run -- --smoke-test          # bounded ~8s run, prints an fps/frame-time summary, exits cleanly
dotnet run -- --diagnostic baseline # same, plus writes DiagnosticReports/Baseline_<timestamp>/REPORT.md
dotnet run -- --diagnostic visual   # bounded 3-phase visible-frame check (solid color / gradient / world), writes screenshots + REPORT.md
dotnet run -- --profile Safe --smoke-test   # P1: run at a named performance profile (Safe/Balanced/High, default High) - any bounded mode above accepts --profile
dotnet run -- --diagnostic perf-sweep       # P1: 10 bounded sub-runs per profile (Safe, High), ~2 min total, writes DiagnosticReports/PerfSweep_<timestamp>/raw_results.csv + summary.txt
dotnet run -- --world LavaLamp --smoke-test # pick a world (StellarNursery/LavaLamp, default StellarNursery) - any bounded mode above, and perf-sweep, accepts --world; unknown name prints a warning and falls back to StellarNursery rather than crashing
dotnet run -- --dashboard-only               # Dashboard-Only Launcher Mode (AUDIT.md Entry 24): starts only AudioEngine + ControlServer and opens http://localhost:8080 - no GameWindow/world is constructed until a scene is picked from the dashboard. See Engine/DashboardHost.cs.
./run-show.sh                               # Scene Dashboard v0.1: unbounded "show mode" - now runs dotnet run -- --dashboard-only in the background (was --profile Safe until Entry 24; changed because auto-starting Stellar Nursery on launch was unwanted), then auto-opens http://localhost:8080 (or prints the URL if auto-open fails). Desktop Launcher Usability Pass (AUDIT.md Entry 22): robust symlink/alias-following path resolution, dependency checks, duplicate-running-instance detection, poll-based dashboard-ready detection, output logged to DiagnosticReports/launcher_last_run.log on failure. "Run Cosmic Engine.command" is the double-clickable Finder wrapper around it - see README_LAUNCHER.md for end-user (double-click, no Terminal) instructions.
dotnet run -- --diagnostic motion           # Stellar Nursery Showability Audit: bounded, world-agnostic - runs the real (non-debug) render path and captures the actual back buffer at t=1s/5s/15s, writes DiagnosticReports/Motion_<timestamp>/REPORT.md with per-pixel frame-diff stats between captures; answers "does this world visibly move" with evidence instead of assertion
dotnet run -- --world StellarNursery --seed 777 --diagnostic motion  # Stellar Nursery Showability Consistency Fix: --seed <value> sets COSMICENGINE_SEED for this run - makes any run (normal, dashboard, or bounded diagnostic) reproducible instead of picking randomly from KnownGoodSeeds; the active seed is now logged in every --diagnostic visual/motion REPORT.md
```

There is no test project and no lint config in this repo.

**Do not leave Cosmic Engine running after diagnostics or tests.** Prefer bounded commands such as `dotnet run -- --smoke-test` or `dotnet run -- --diagnostic baseline`/`--diagnostic visual`. If normal `dotnet run` is used, run it only for a bounded manual check and explicitly stop/close the process before reporting completion — it does not exit on its own (see `Engine/CosmicEngine.cs`).

**macOS AMFI / Gatekeeper note (Mac AMFI Apphost Workaround Pass, `AUDIT.md` Entry 37):** on macOS Tahoe 26.5.2, the locally-built .NET apphost binary (`bin/Debug/net8.0/CosmicEngine.App`) is ad-hoc signed, which AMFI/Gatekeeper can reject at `exec()` time (SIGKILL, exit 137, zero stdout/stderr, before any Cosmic Engine code runs — see `AUDIT.md` Entries 35/36 for the original investigation). Two changes address this, both already applied in this repo: (1) `CosmicEngine.App.csproj` sets `<UseAppHost>false</UseAppHost>`, so that ad-hoc-signed apphost is never generated, and as a side effect `dotnet run` itself now works (it internally execs via the trusted `dotnet` host rather than the apphost); (2) `run-show.sh`/`Run Cosmic Engine.command` now build once, then launch the built `.dll` directly via `dotnet <dll-path>` rather than `dotnet run`, for the same reason, belt-and-suspenders. If `dotnet run` or the launcher ever silently SIGKILLs again with empty output on a Mac, suspect this same AMFI mechanism first (e.g. after `UseAppHost` gets reverted, or a distributed/notarized build path is introduced) before assuming a code regression.

**macOS display-sleep note (found during Abyssal Bloom Phase 4, `AUDIT.md` Entry 47):** if `dotnet run`/the built `.dll` starts crashing with a bare `Segmentation fault: 11` (exit 139) and zero stdout — including on worlds/code paths that were not touched by the current session, which rules out a code regression — check whether the physical display has gone to sleep (`system_profiler SPDisplaysDataType | grep Asleep`; `Display Asleep: Yes` confirms it). Creating an OpenGL window/context while the display is asleep reliably segfaults on this machine. This is most likely to happen during a long unattended agent session with no real user present to generate input. Fix: run `caffeinate -u -di -t <seconds>` in the background for the remainder of the session (`caffeinate -u -di -t 1800 & disown`) to keep the display awake; crashes stop immediately and do not require any code change.

## Operating rules (governance)

These rules were formalized after the 2026-07-06 Fable strategy review (see `AUDIT.md` Entry 12 and
`ROADMAP.md`) in response to repeated open-ended shader-iteration cycles with contested visual payoff.
They apply to every pass, not just visual/shader work:

1. Do not leave Cosmic Engine running after diagnostics or tests.
2. Prefer bounded runs: `--smoke-test`, `--diagnostic baseline`, or specific diagnostic commands.
3. Do not push to GitHub without explicit user approval.
4. Do not self-sign `AUDIT.md` reviewer sign-off — the implementation model never signs its own audit entry.
5. No visual pass is accepted without screenshots.
6. No performance claim is accepted without FPS/frame-time evidence — and evidence means repeated runs (a distribution), not a single reading.
7. No hardware-viability claim is accepted without running on the actual target hardware.
8. Do not accept "non-black pixels" (or any similarly weak proxy metric) as visual success.
9. Commit by intent whenever possible — one concern per commit, not large mixed commits.
10. Do not let shader-art debugging continue indefinitely. If a visual pass fails acceptance twice, or exceeds one agent-day, stop and escalate to the user/ChatGPT with a written options memo instead of continuing to iterate.
11. Infrastructure passes (RenderScale, diagnostics, profiles, etc.) must not include shader-art changes.
12. Shader-art passes must not include unrelated infrastructure changes.
13. If visual payoff is weak relative to the shader complexity being added, stop and escalate rather than adding more procedural noise.
14. Use bounded profile commands for performance testing (`--profile <name> --smoke-test`/`--diagnostic baseline`, or `--diagnostic perf-sweep` for repeated-run evidence) — see `AUDIT.md` Entry 13 (P1) for why single-run readings on this project have repeatedly produced misleading "stable" numbers that hid real variance.
15. Do not make a performance or profile-comparison claim from a single run of any profile — P1's own sweep showed one profile's single-run FPS can land anywhere in a 3x range depending on the run; always cite a run count.
16. Profile/infrastructure passes (RenderScale, diagnostics, perf-sweep, etc.) must not include shader-art changes — see rule 11.

Note: shader files are loaded from disk at runtime via relative paths (e.g. `Worlds/World01_StellarNursery/Shaders/...`), not copied/embedded by the build. Always run `dotnet run` with this directory as the working directory, otherwise shader loading will fail with `FileNotFoundException`.

## Runtime dependencies

- **Audio input**: `Audio/AudioEngine.cs` opens an OpenAL capture device (stereo, 44.1kHz) and expects a real two-channel guitar interface (originally tuned for a Focusrite Clarett — see `Tuning.cs` comment). Running without a capture device attached will throw at startup (`AudioEngine: could not open capture device`).
- **GPU/OpenGL**: rendering is via OpenTK/OpenGL 4. `Rendering/ShaderProgram.cs` throws on shader compile/link failure with the GL info log inlined in the exception message — read that message first when a shader doesn't build.

## Architecture

**Engine loop** (`Engine/CosmicEngine.cs`, class `CosmicEngineApp`): owns the OpenTK `GameWindow`, the `Camera`, and the single active `IWorld`. Each frame: build an `AudioSignal` snapshot from `AudioEngine` → `_camera.Update()` → world renders into a fixed 1280x720 `RenderTarget` → that target is blitted (scaled) to the actual window framebuffer. This means shader cost is constant regardless of window/display size, and resizing the window is purely a blit-scale operation, not a re-render.

**Worlds** (`Engine/IWorld.cs` + `Worlds/`): a "world" is a self-contained visual scene implementing `Load()/Update()/Render()/Unload()`. Adding a new world means implementing `IWorld` and registering it in `Engine/SceneRegistry.cs` (a `SceneDefinition` with Id/DisplayName/Description/Status/DefaultProfile/Showable/Factory) — `Engine/WorldSelector.cs` (`ValidNames`/`Create()`, used by `--world` CLI parsing) is a thin wrapper over `SceneRegistry`, so registering a scene there is enough for both the CLI and the dashboard to pick it up; nothing else in the engine needs to change. Four worlds exist:
- `Worlds/World01_StellarNursery/StellarNursery.cs` (namespace `CosmicEngine.App.Worlds.World01`, folder `World01_StellarNursery` — naming isn't 1:1, keep this in mind when searching) — the default, a volumetric raymarched nebula.
- `Worlds/World02_LavaLamp/LavaLampScene.cs` (namespace `CosmicEngine.App.Worlds.World02`) — a cheap analytic 2D metaball-field scene, added as a multi-world architecture proof (see `AUDIT.md` Entry 14).
- `Worlds/World03_WindTurbineFire/WindTurbineFireScene.cs` (namespace `CosmicEngine.App.Worlds.World03`) — a shader-only industrial-nightmare tableau, wind-turbine silhouettes against smoke with a slow-building ember horizon (see `AUDIT.md` Entries 30-39).
- `Worlds/World04_Underwater/UnderwaterScene.cs` (namespace `CosmicEngine.App.Worlds.World04`, registered scene Id `Underwater`, `DisplayName`/`Description` updated to "Cosmic Reef") — a shader-only underwater-to-cosmic scene: Phase 1 atmosphere (god rays, caustic shimmer, marine-snow particulate), Phase 2 jellyfish (SDF bell + traveling-wave tentacles, `AUDIT.md` Entry 41 and addenda), and Phase 3 foreground refraction/caustic-ray polish (`AUDIT.md` Entry 43) are all committed; a further "Living Water" pass added C#-integrated jellyfish drift paths, camera parallax, and a plankton bloom field (`AUDIT.md` Entry 44, committed `e1c576b`). A "Bloom refinement" pass on top of that gives the plankton field flow-coherent current-channel streaming and traveling pulse-train brightness waves plus a dedicated spatial early-out performance fix (`AUDIT.md` Entry 45 and its addendum, committed `faddaba`). An "Abyssal Bloom Phase 3" pass adds a distant, irregular, domain-warped field of abyssal glow low in the water column, gated across the same `uBloom` arc every other layer already uses and deliberately abstract/atmospheric rather than creature-like (`AUDIT.md` Entry 46, committed `fed7a7d`). An "Abyssal Bloom Phase 4 'Presence / Color / Depth Population'" pass adds a distant "alien presence" shadow layer (a darkening mix, not a glow, gated by its own independent `uTime`-only "appears every few seconds" cycle layered on top of the bloom arc), several cheap reduced-detail background jellyfish (shader-hash-placed, not running the foreground tentacle pipeline), and small color-variation nudges across existing layers, plus a compositing-order visibility fix (`AUDIT.md` Entry 47 and Addendum 1, committed `28f3e43`). A **"Cosmic Reef Pivot Phase 1"** pass — approved architect plan, **not yet committed, not ready for review** — adds a second `uCosmic` accumulator (rises once `uBloom` exceeds 0.65, tied to the same evolution-length dashboard slider as bloom) driving a cosmic-breach starfield, a nebula retint of the abyssal glow field, a scene-level color-bloom wave, drifting multi-bend ribbon organisms, and a hero-jellyfish demotion scalar as the breach opens (`AUDIT.md` Entry 48). **Known open issue: the mandatory 60fps performance floor is not met at High profile during sustained high bloom** (~50fps measured vs. the required ≥60fps) — see Entry 48's options memo before treating this pass as complete.

Each world owns its own `ShaderProgram`, keeps its own smoothed/calibrated copies of the audio signal, and pushes them to the shader as uniforms every frame. `--world <name>` (see Commands above) selects which world `CosmicEngineApp` constructs via `WorldSelector.Create(name, camera)`; the default (no flag) is `StellarNursery`, unchanged from before world-selection existed.

**Audio pipeline** (`Audio/`): `AudioEngine.CaptureLoop()` runs on a dedicated background thread, does an FFT per buffer (MathNet.Numerics), and exposes two `GuitarChannel`s (`Guitar1`/`Guitar2`, `volatile` fields) with `Level`/`Bass`/`Mid`/`Treble`. `AudioSignal` (in `Audio/AudioSignal.cs`) is the per-frame immutable snapshot passed into `IWorld.Update()`. By convention across worlds: **Guitar 1 = "Creator"** (energy/color/ignition), **Guitar 2 = "Sculptor"** (gravity/structure/motion) — this is a semantic convention, not enforced in code, so preserve it if you add a world.

**Calibration / tuning**: raw FFT band energies are not directly usable — each world applies a floor/max calibration (`Calibrate()` in `StellarNursery.cs`: `(raw - floor) / max`, clamped 0–1) before sending to the shader, then smooths with an exponential lerp. Baseline calibration constants live in `Tuning.cs` (static, mutable at runtime) and are also duplicated as world-local constants in `StellarNursery.cs` — `Tuning.cs` values are the ones live-adjustable via the control server; the world-local constants are its own copy used elsewhere in `Update()`. Don't assume these two sets are kept in sync automatically. Calibrated Audio Reactivity Integration v0.1 (`AUDIT.md` Entry 27): both worlds also read `Audio/CalibrationEngine.cs`'s `InputA`/`InputB.CurveOutput` directly (see below) and add a capped, modest contribution (`CurveOutput * CalibrationEngine.CalibratedBlendWeight`) on top of the `Tuning.cs`-derived values above, clamped to 1.0 — additive, not a replacement; zero effect under silence since `CurveOutput` is 0 at rest. This is a second, independent calibration layer from the `Tuning.cs` one — don't conflate the two.

**Live control panel + Scene Dashboard** (`ControlServer.cs`): a plain `HttpListener` on `http://localhost:8080` (no framework) serving a single self-contained HTML page. Two sections: (1) the original audio-tuning sliders bound to `Tuning.*` fields via `POST /set`/`GET /values` — if you add a new tunable, add it to `Tuning.cs`, the `switch` in `ControlServer.Handle`, the `/values` serializer, and the HTML slider markup; (2) the Scene Dashboard v0.1 section — `GET /status` (current world/profile/fps/render target/audio status, read from `CosmicEngineApp.Current`), `GET /scenes` (from `SceneRegistry.All`), `POST /launch` `{sceneId, profile}`, `POST /restart`, `POST /quit`. Launch/restart/quit calls just set thread-safe volatile fields on `CosmicEngineApp` (`RequestSwitch`/`RequestRestart`/`RequestQuit`) from ControlServer's background HTTP thread; the actual world/profile switch happens once per frame in `CosmicEngineApp.OnRenderFrame` → `ApplyPendingSwitch()`, on the render thread, since that's the only thread allowed to touch GL resources. This is **live, in-process** scene and profile switching (no restart) — see `AUDIT.md` Entry 15. Dashboard-driven requests are inert during any bounded `--smoke-test`/`--diagnostic` run. Dashboard Show Seed Support (`AUDIT.md` Entry 19): scenes may declare a `SceneDefinition.ShowSeed` (Stellar Nursery: `"777"`, Lava Lamp: `null`) — applied automatically at initial startup (unless an explicit CLI `--seed` was given) and on every dashboard-driven world switch, via the same `COSMICENGINE_SEED` override `--seed` uses. `GET /status`/`GET /scenes` expose the active/default seed; the dashboard shows it in the status bar and on scene cards. Plain CLI launches with no `--seed` still use `StellarNursery.Load()`'s random `KnownGoodSeeds` pool, unchanged. Dashboard-Only Launcher Mode (`AUDIT.md` Entry 24): `POST /launch`/`POST /quit` route to `Engine/DashboardHost.cs`'s own `RequestLaunch`/`RequestQuit` instead of `CosmicEngineApp.Current?...` whenever `CosmicEngineApp.Current` is null (i.e. no scene has been launched yet, such as right after `--dashboard-only` startup) — `DashboardHost` then constructs the first `CosmicEngineApp` (via `RunFromDashboardHost`) on the main thread, since GameWindow/GL creation must happen there on macOS. Once a scene is running, `/launch`/`/quit` fall back to the pre-existing in-process path unchanged. Dashboard Calibration Tab v0.1 (`AUDIT.md` Entry 26): a third dashboard section, deliberately separate from both the `Tuning.*` sliders and the Scene Dashboard — `GET /calibration/status` and `POST /calibration/channels|manual|preset|curve|reset|testinput`, backed by `Audio/CalibrationEngine.cs` (selects which 2 of the currently-available audio channels drive "Input A"/"Input B", self-starts a ~30Hz background timer via a static constructor - guaranteed by the CLR on first access to any static member of the type, so both dashboard endpoint calls and a scene directly reading `CalibrationEngine.InputA` are equally sufficient to start it) and `Audio/InputCalibration.cs` (per-input gain/gate/smoothing/ceiling, a cubic-Bezier response curve with two draggable control points, live raw/smoothed/peak/clip/post-curve-output tracking, and a `TestOverrideRawLevel` for the dashboard's labeled "Send Test Pulse" button, which injects a synthetic level through the same real pipeline instead of a shortcut). This answers "how loud is this input and how do we map it to 0-1", not "how should a scene react to that value" — see `AUDIT.md` Entry 26 for the full scope, including that only 2 channels are currently capturable (stereo OpenAL) regardless of how many inputs the connected interface has. As of Calibrated Audio Reactivity Integration v0.1 (`AUDIT.md` Entry 27), both `StellarNursery.cs` and `LavaLampScene.cs` *do* consume `CalibrationEngine`'s post-curve output (see "Calibration / tuning" above) — `GET /status` also now exposes `calibratedA`/`calibratedB`/`sceneAudioSource` so the dashboard's Scenes tab can show what each running scene is actually using. Calibration Presets v0.1 (`AUDIT.md` Entry 28) added named, full-setup preset save/load/delete — `GET /calibration/presets` and `POST /calibration/presets/save|saveas|load|delete`, backed by `Audio/CalibrationPreset.cs` (the data model - `CaptureCurrent()`/`ApplyTo()`, with numeric clamping and channel-fallback validation on load) and `Audio/CalibrationPresetStore.cs` (JSON persistence at `Config/calibration-presets.json`, relative to the working directory like every other relative path in this codebase - not tracked in git, see `.gitignore`; corrupt files are quarantined with a timestamp and never silently discarded; 4 built-in presets are seeded only if the file doesn't exist yet). Loading a preset mutates `CalibrationEngine.InputA`/`InputB` in place, so it reaches a running scene's next frame with no restart.

- `Worlds/World05_HybridTest/HybridTestScene.cs` (namespace `CosmicEngine.App.Worlds.World05`, registered scene Id `HybridTest`) — Phase 1 "Hybrid Proof" prototype (video-atoms `MILESTONE_BREAKDOWN.md`): composites one hardcoded `VisionBoard/` clip (via the new `Rendering/Video/IVideoDecoder`/`FfmpegPipeDecoder`/`VideoTexture` seam) with a StellarNursery child world rendered into a private `RenderTarget`, mixed by `Tuning.HybridBlend` in a single-uniform composite shader. **Not evidenced as a real hybrid-video pass yet** — ffmpeg is not installed on the current dev machine, so this scene has only ever run its non-fatal synthetic-fallback-color path; see `AUDIT.md`'s Phase 1 entry before treating it as complete. ffmpeg was subsequently installed on this dev machine and real-decode playback was validated (`AUDIT.md` Entry 49 Addendum). A Phase 3 "Effect Stack v1" pass (`AUDIT.md` Entry 50) added uniform-driven grayscale/mirror-X/mirror-Y/lift-gamma-gain grade/vignette to `hybrid.frag`, applied after the unchanged Phase 1 blend, plus a `PlaybackSpeed` (0.25x-2x) property on `IVideoDecoder`/`FfmpegPipeDecoder` implemented as decode-rate pacing on the reader thread (not a shader effect, per `VIDEO_SYSTEM_ARCHITECTURE.md` §2.2) - all wired to the dashboard via new `Tuning.cs`/`ControlServer.cs` sliders under an "Effects" section, scoped to World05 only.

**Camera** (`Engine/Camera.cs`): a slow, layered sine/cosine drift + zoom (three superimposed frequencies each axis) applied independently of audio, giving worlds a continuous ambient motion; worlds read `Camera.Zoom`/`Camera.Offset` and pass them into shaders as uniforms rather than transforming geometry directly (there is no geometry — everything is fullscreen-quad fragment shader work). Note this 2D drift/zoom camera is separate from — and currently unused by — `stellar_nursery.frag`'s own 3D raymarch camera basis (`uCamPos`/`uCamForward`/`uCamRight`/`uCamUp`), which `StellarNursery.cs` sets directly with a fixed placement. `Camera.Update()` is called unconditionally every frame by the engine loop regardless of which world is active, so `Camera.Offset` is always live even for worlds that don't read it — as of Underwater Phase 1 "Living Water" (`AUDIT.md` Entry 44), `UnderwaterScene`/`underwater.frag` is the first world to actually consume it, as a per-layer parallax coordinate shift (not rotation/zoom); Stellar Nursery/Lava Lamp/Wind Turbine Fire still do not read it.

**Runtime diagnostics** (`Engine/CosmicEngine.cs`): `Program.cs` passes `args` into `CosmicEngineApp.Run(args)`, parsed by `ParseArgs`. Three bounded modes exist beyond normal `dotnet run`: `--smoke-test` (fixed-duration run + fps summary), `--diagnostic baseline` (same, plus a `REPORT.md`), and `--diagnostic visual` (cycles solid-color → debug-gradient-shader → normal world, capturing a screenshot and luminance reading per phase — see `Diagnostics/Shaders/` for the isolated debug shader used in the gradient phase). All three force `Environment.Exit(0)` in `OnUnload` as a deliberate belt-and-suspenders measure so bounded runs never leave the process alive.
